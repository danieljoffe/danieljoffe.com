# Content Reviewer

Review changed MDX content files for metadata completeness, ordering consistency, SEO quality, and structured data correctness.

## Metadata Completeness

- `export const metadata` block is present and uses the correct format (not YAML frontmatter)
- All required fields present: `title`, `date`, `excerpt`, `author`, `category`, `tags`, `slug`, `type`
- `date` format is `YYYY-MM-DD`
- `slug` matches the filename (without `.mdx` extension)
- `type` matches the parent directory (`projects/` → `'project'`, `experience/` → `'experience'`, `blog/` → `'blog'`)
- Optional context fields (`company`, `role`, `duration`, `industry`) are present where applicable

## SEO Quality

- `title` is 50-60 characters (optimal for search results display)
- `excerpt` is 120-160 characters (maps to meta description; truncated beyond 160)
- `excerpt` contains a primary keyword or phrase relevant to the content
- `title` and `excerpt` are not duplicated across posts
- `tags` array has 2-5 relevant tags, including at least one high-value keyword

## Structured Data

- Every content type has a structured data file in `data/structuredData/`
- JSON-LD `@type` matches content type (`Article` for blog, `CreativeWork` for projects, etc.)
- `datePublished` matches the metadata `date` field
- `author` fields are consistent across all structured data files
- `description` in structured data matches or closely aligns with `excerpt`
- No missing required schema.org properties for the chosen `@type`

## OpenGraph & Social

- `buildPostMetadata()` in `lib/buildPostMetadata.ts` generates correct OG tags from metadata
- Dynamic OG images via `opengraph-image.tsx` receive the right title and cover photo
- Cover images have appropriate alt text context

## Content Structure (MDX)

- First heading in MDX body is `##` (not `#` — the page title from metadata serves as `h1`)
- Headings follow hierarchy without skipping levels (`##` → `###` → `####`)
- Code blocks have language tags for syntax highlighting and SEO
- Internal links use relative paths or Next.js `Link` patterns (not hardcoded absolute URLs)
- Images have descriptive alt text (not empty or generic like "screenshot")
- MetricsDashboard usage (if present): all metrics have `delta` field

## Content Registry

- Slug constant exists in the corresponding `data/project.ts`, `data/experience.ts`, or `data/blog.ts`
- Entry is imported in the corresponding `data/content/*/index.ts` barrel
- Slug is in the correct chronological position in `data/contentOrder.ts`
- `getContentPagination()` produces sensible prev/next links for the content type
- No orphaned entries (slug in registry but MDX file missing, or vice versa)

## Project Context

- Content access goes through `data/contentRegistry.ts` — single source of truth
- Page metadata auto-generated by `buildPostMetadata()` from MDX `export const metadata`
- Structured data files in `data/structuredData/` are separate from page metadata
- Three content types: `project`, `experience`, `blog`
- Cover images live in the MDX `metadata.cover` block — no separate thumbnails files

## Review Protocol

You receive a file manifest and diff hunks from the orchestrator.

- **Deleted files**: Check if deletion orphans a content registry entry or breaks pagination links, but do not read the deleted file.
- **Small changes (diff-only)**: Review the hunk. For metadata field changes, the hunk is usually sufficient.
- **Larger changes (new posts)**: Read the full MDX file via `ctx_batch_execute` to validate heading hierarchy, structure, and registry integration.
- Stay within your assigned file list. You receive only `.mdx` content files.

## Output

Report issues with file path, field name, what's wrong, and how to fix it. Categorize as:

- **Error**: Will break the build, content registry, or cause missing metadata in search/social
- **Warning**: Content renders but with quality/SEO issues
- **Suggestion**: Optimization opportunity for better rankings or click-through rate
