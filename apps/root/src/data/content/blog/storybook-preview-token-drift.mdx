## The problem

I already test design-token contrast. A jest spec reads my shipped theme CSS, converts every oklch token to sRGB, and asserts each text-on-tint pair clears 4.5:1. It runs in the fast CI lane in milliseconds, and it stays green.

So when a design review flagged my dark-mode warning and error badges as muddy and sitting right on the floor, the test gave me nothing. `--color-error` on `--color-error-light` measured 4.70:1 and passed. The reviewer was looking at the same component and seeing something worse, so one of us was reading the wrong number.

The reviewer was right. They were looking at Storybook, and Storybook does not render the stylesheet my test reads.

## The approach

My shared-ui library ships `pyre-theme.css`. Storybook renders its canvas from a second file, `pyre-storybook-preview.css`, copied off the theme so the demo carries the brand. Two files, one source of truth in theory.

In practice they'd drifted. The shipped theme's dark error tint was `oklch(0.24 0.1 25)`; the preview's was `oklch(0.25 0.05 25)`, with different chroma, different luminance, and different contrast. My test parses `pyre-theme.css` and `indigo-theme.css`, and it never opens the preview file. So the 4.70:1 it guarded was the shipped value, while the 4.53:1 the reviewer saw, a hair above the floor, lived in a file no test ever touched.

The test wasn't wrong; it was vouching for a stylesheet nobody actually looks at.

## The implementation

The contrast math is the same arithmetic the spec already runs: oklch to sRGB to relative luminance to a ratio. Running it on both files told the real story; the shipped error tint came out at 4.70:1 and the demo error tint at 4.53:1, two numbers for one component.

So I collapsed both files onto a single set of values, tuned to fix the muddiness the review actually flagged. Dropping chroma pulls the brown and maroon cast out of the tint, and lowering the error surface's luminance buys contrast margin, since the text is the lighter half of the pair.

```css
/* pyre-theme.css AND pyre-storybook-preview.css, .dark */
--color-warning-light: oklch(
  0.3 0.055 72
); /* was 0.32 0.08 70 shipped / 0.28 0.05 70 demo */
--color-error-light: oklch(
  0.21 0.055 25
); /* was 0.24 0.1 25 shipped / 0.25 0.05 25 demo */
```

Error text-on-tint lands at 5.00:1 in both files. Warning reads clean at 6.66:1.

Editing two files by hand is a patch, not a fix; they'll just drift again the next time I touch one. The durable options are to point the contrast test at the preview file too, so the demo lives under the same contract, or to delete the duplicate and let Storybook import the shipped theme directly. The copy only exists for branding reasons I can solve other ways, so the real move is to stop maintaining a stylesheet I can render but never test.

## The result

- One set of tint values across the shipped theme and the Storybook demo.
- Dark error contrast from 4.53:1 to 5.00:1, warning de-mudded, both clear of AA.
- The number CI reports and the color the demo shows finally describe the same component.

## The takeaway

A test guards the files it parses and nothing else. If your showcase renders from a copy, that green check is signing off on a stylesheet no one ever sees. Test the artifact you actually put on screen, or stop keeping a separate one to put there.
